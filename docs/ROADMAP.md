# Spellcraft PoC 後續擴充與美術遷移計畫

> 本文件補充 `DESIGN.md`，聚焦在兩件事：**(1)** 目前用程式繪圖（placeholder art）做的畫面，之後要怎麼換成正式美術資源；**(2)** 玩法/系統還缺哪些東西、建議的優先順序。閱讀前請先讀過 `DESIGN.md` 第3節（核心機制），本文件不重複說明已拍板的設計決策。

---

## 1. 美術現狀：為什麼全部是程式繪圖

目前專案裡沒有任何圖片/美術資源檔案（沒有 `.png`、`.svg`、無 `Sprite2D`/`AnimatedSprite2D`），所有視覺呈現都是用 Godot 的 `_draw()` 即時程式繪製幾何圖形（三角形、圓形、多邊形）加上 `CPUParticles2D` 動態粒子。這是刻意的 PoC 做法：**先驗證玩法與互動手感，不花時間等美術資源**。

這個做法的問題很直接：
- 畫面辨識度低、無法傳達最終美術調性給非開發者（例如給別人看 Demo 時容易被誤判為「做得很粗糙」而非「刻意的 PoC 範圍」）。
- `_draw()` 寫在遊戲邏輯腳本（`Player.gd`、`TargetDummy.gd`...）裡，程式碼跟視覺綁在一起，之後要換真實美術時，等於要動到核心邏輯檔案，風險較高。
- 沒有動畫系統（`AnimationPlayer`/`AnimatedSprite2D`），所有「動態效果」都是用數值運算模擬（例如 `squash`/`jump_height`/`hat_bob`），無法做出真正有幀數設計的動畫。

**好消息**：因為遊戲邏輯（狀態機、傷害計算、符紋判定）跟繪圖呼叫（`_draw()`）在程式碼結構上是分離的——邏輯只負責改變數值變數（`is_casting`、`squash`、`jump_height`...），`_draw()` 只負責讀這些變數畫圖——所以**替換美術資源時，理論上不需要碰邏輯部分，只需要替換/刪除 `_draw()` 內容**。下一節說明具體怎麼做。

## 2. 美術遷移計畫：從程式繪圖換成正式資源

### 2.1 每個檔案目前用程式繪圖呈現什麼、換成美術後該怎麼做

| 檔案 | 目前程式繪圖內容 | 建議換成 | 遷移方式 |
|---|---|---|---|
| `Player.gd` | 三角長袍+尖帽+法杖，用 `robe_color`/`glow_color`/`hat_bob`/`cast_pulse` 等變數驅動繪製 | `AnimatedSprite2D`，含 Idle/Move/Cast/Hit 等動畫狀態 | 把 `CharacterBody2D` 底下加一個 `AnimatedSprite2D` 子節點；在對應的狀態切換處（`_start_casting`/`_cancel_casting`/`take_damage`等）呼叫 `sprite.play("cast")` 之類的動畫，取代目前靠變數在 `_draw()` 裡算顏色/形狀的做法。`_draw()` 整個函式可以刪除。 |
| `SpellProjectile.gd` | 發光球體+環繞光點，顏色依效果變化（`orb_color`） | 一組法術彈道 Sprite（可能依元素/強化效果有不同貼圖或色調） | 新增 `Sprite2D` 子節點，`orb_color` 可以保留用於 `modulate` 著色（如果美術資源設計成灰階+用程式上色，可以沿用現有顏色邏輯，省去多套圖）。 |
| `TargetDummy.gd` | 水晶怪物造型，`squash`/`jump_height`/`idle_bob` 驅動擠壓與跳躍動畫 | 怪物 `AnimatedSprite2D`（Idle/Telegraph/Jump/Slam/Hit 動畫） | 狀態機（`AiState` enum）已經存在且與美術無關，直接在 `_enter_state()` 對應位置加上 `sprite.play(...)` 呼叫即可，狀態機邏輯完全不用改。警示圈（`draw_circle`/`draw_arc` 畫的範圍指示）建議**保留程式繪圖**，不建議做成美術資源——範圍指示通常用簡單幾何+shader 即時生成效果最好維護，很多商業遊戲也是這麼做。 |
| `Arena.gd` | 程式生成灰色磚塊紋理（固定 seed 隨機明暗） | Godot `TileMap` + `TileSet`，使用真正的石磚貼圖素材 | 這塊改動最大，建議整個場景從「一張程式畫的大圖」改成「TileMap 鋪真實磚塊貼圖」。牆體碰撞（`Walls` 的 `StaticBody2D`）邏輯不受影響，可以照舊沿用，只是外觀換成貼圖對齊。 |
| `MagicFX.gd` | `CPUParticles2D` 用純色圓點模擬粒子爆發/拖尾 | 用美術設計的粒子貼圖（`texture` 屬性），或維持 `CPUParticles2D` 但換成含材質的版本 | `spawn_burst()`/`make_sparkle_trail()` 這兩個 helper 的參數介面（`parent, pos, color, amount, speed`）可以完全不變，只需要在內部幫 `CPUParticles2D` 加上 `texture` 屬性指向美術資源，呼叫端（`Player.gd`/`TargetDummy.gd`/`SpellProjectile.gd`）完全不用改。 |
| UI (`Main.tscn`/`Main.gd`) | 純 Godot 內建 `ProgressBar`/`Label`，沒有自訂樣式 | 自訂 `Theme` 資源，套用美術設計的 UI 框架/字體/圖示 | Godot 的 `Theme` 系統可以整組套用，不需要逐個節點改，建議美術資源確定後直接做一份 `.tres` Theme 檔套用到 `UI` CanvasLayer 下所有節點。 |

### 2.2 建議的遷移順序
1. **先做 Arena 地板/牆**（視覺影響最大、玩家第一眼看到的東西，且跟遊戲邏輯幾乎無關，風險最低）。
2. **角色與怪物的靜態造型**（換掉三角形/水晶多邊形，先上靜態圖，不急著做動畫）。
3. **角色與怪物的動畫**（Idle/Cast/Jump/Hit 等狀態動畫，需要美術產出對應幀數或 Spine/骨骼動畫）。
4. **法術特效與粒子**（優先度較低，程式粒子效果在 PoC 階段已經堪用）。
5. **UI Theme**（最後做，因為 PoC 階段 UI 只是功能性顯示，不影響核心手感測試）。

### 2.3 給美術的風格提示（延續 Magicka 調性決策）
- 調性：Q 版、鮮豔飽和色、誇張比例（大頭小身體、誇張法術特效），避免寫實/黑暗風格。
- 色彩分工目前已經用程式碼隱含定義，美術資源設計時建議沿用，保持辨識度一致：
  - 符紋效果色：傷害=紅、爆炸/範圍=橘、強力/爆發=粉紫/金黃、吟唱加速=青、吟唱減速=藍紫。（穿透、投射物彈速機制都已移除，見 `SPELL_SYSTEM.md` §8.7、§8.8；吟唱速度是新加的，見 §8.9，跟投射物彈速是不同概念）
  - 角色狀態色：吟唱中=紫、符紋成功=綠閃、符紋失敗=紅閃、受到怪物攻擊=橘閃。
- 怪物目前暫定「水晶系」造型，但這只是程式繪圖方便（多邊形好畫），**不是美術方向的硬性限制**，正式美術可以重新設計怪物種族/外觀。

## 3. 玩法/系統擴充清單（取代並更新 DESIGN.md 第6.2節的待辦）

以下項目依照目前判斷的優先順序排列，括號內註記是否與美術遷移有依賴關係。

### 3.1 高優先（直接影響核心玩法驗證完整度）
1. **玩家 HP 系統**：目前玩家被怪物範圍攻擊打中只有視覺回饋（`take_damage` 在 `Player.gd` 裡只閃光噴粒子），沒有實際扣血。要驗證「立回」這個 PVE 核心玩法，必須有真正的生死壓力。
2. **怪物攻擊模式擴充**：目前只有一種「起跳+範圍落地傷害」，需要至少 2-3 種不同節奏/判定方式的攻擊（例如：直線衝撞、小範圍連續攻擊、遠程投射），才能驗證「吟唱中打符紋」在面對多樣化威脂時是否還好玩，而不是只能應付單一種可預期的攻擊。
3. **吟唱被打斷的正式判定**：目前決策是「範圍攻擊不會中斷吟唱，只扣血」，但這只在「單一種攻擊、傷害可承受」的前提下合理。一旦加入 HP 系統與更強的怪物攻擊，需要重新評估——不是所有攻擊都該不會打斷吟唱，可能需要分「輕擊＝不中斷」「重擊＝中斷」兩個等級。
4. **符紋組合表的設計擴充**：目前只有6組純示範數值，需要和「法術欄位／裝備系統」的框架一起設計，否則無法測試「快唱 vs 慢唱」兩種 Build 的差異化體驗（這是原始構想裡的核心賣點之一，PoC 目前完全沒有觸碰）。

### 3.2 中優先（完整度相關，但不急著在這波 PoC 做）
5. **法術切換圓盤**（Ctrl 選盤，仿 Witcher 3）：目前只有一個固定裝備法術，沒有切換機制，正式玩法需要。
6. **範圍型法術與俯視選圈**：原始設計的另一種法術型態，目前完全未實作，涉及鏡頭切換與遊戲暫停邏輯，工作量不小。
7. **Dash／空白鍵機動技能**：影響怪物攻擊迴避的手感，跟「3.1 第2項怪物攻擊模式擴充」綁在一起测試比較有效率。
8. **多隻怪物同時戰鬥**：目前場地只放了一隻固定怪物，`_find_player_position()` 目前假設只有一個 `player` group 成員，若要測試多怪物圍攻，需要先確認現有 group 查找邏輯沒有依賴單一怪物的假設（目前看起來沒有，但未實測）。

### 3.3 低優先（本次 PoC 範圍外，記錄供未來正式開發參考）
9. 裝備與符紋掉落、強化（解放）系統——完整的「打王→掉素材→變強」ARPG 循環。
10. 職業系統、法術學習限制。
11. Mana／施放頻率限制系統。
12. 怪物死亡/擊殺邏輯（目前打到0血直接重置滿血，純粹方便連續測試用）。

## 4. 本文件與 DESIGN.md 的關係

- `DESIGN.md`：記錄**已經做的決策與原因**（核心機制設計、數值演進歷史、已知行為邊界），是「這個東西現在為什麼長這樣」的真相來源。
- `ROADMAP.md`（本文件）：記錄**還沒做、接下來要做什麼**，包含美術資源遷移路徑與玩法擴充清單的優先順序建議。

兩份文件會隨專案進度一起更新：當 `ROADMAP.md` 裡的項目完成後，應該把對應的設計決策（為什麼這樣做、過程中發現的問題）補寫回 `DESIGN.md`，而不是留在這份路線圖裡。
